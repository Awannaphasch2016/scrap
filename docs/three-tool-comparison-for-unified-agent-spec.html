Three-tool comparison shared surface area for a unified login → get-api agent

After building three concrete tool wrappers — Hyperbrowser (tool #1, 2026-06-05/06), Vercel (tool #2, 2026-06-07), Cursor (tool #3, 2026-06-07) — N=3 is enough data to safely extract the abstraction. This page maps the shared surface area visually so the next implementation step (a single generalized build_login_to_get_api_agent agent) can be specified precisely instead of guessed. Five diagrams from different angles + the resulting unified-agent spec.

Methodology. Three concrete instances give enough diversity to distinguish "truly shared" from "happens-to-match-twice-by-coincidence." N=2 is dangerous because the second instance always looks similar to the first. N=3 with deliberate variation (different OAuth providers, different rendering styles, different token-reveal patterns) is the smallest safe sample for abstraction extraction.

What this shows

  • The middle blue layer is the abstraction. Six shared library files (~1500 LoC) used identically by all three wrappers. Zero per-tool edits to these files (after the day-1 chassis extension this session).
  • Onboarding-doer is loaded by all 3 but only Hyperbrowser actually dispatches it — Vercel and Cursor users were already onboarded. Capability is there; not all tools exercise it.
  • get_api_agent vs create_token_agent split: only Hyperbrowser uses get_api_agent (dashboard-visible key). Vercel and Cursor use create_token_agent (create-then-reveal flow). This is a meaningful per-tool axis.
  • screen_recorder.py is wired into Cursor only so far — should be promoted to default-on for all wrappers (open follow-up).

What this shows

Of the 21 state instances:

  • 15 are universal (5 states × 3 tools): at_signup_or_login, in_google_oauth (also in_github_oauth for one tool, but semantically same role), in_onboarding, blocked_external_gate, unknown. These become the BUILT-IN defaults in the unified agent.
  • 4 are 2-tool shared (2 states × 2 tools): the create-token flow's at_token_list_page/at_api_keys_page and at_token_revealed. These become a SELECTABLE preset ("create-token flow") the unified agent's config can opt into.
  • 3 are tool-specific: Hyperbrowser's at_dashboard_masked_key + at_dashboard_with_visible_key (its dashboard-visible-key flow), Cursor's at_dashboard_other (its sidebar-nav-required flow). These become DECLARED EXTRAS in the tool's per-instance config.

So the unified agent ships with a 5-state DEFAULT vocab (the universal ones) + 1 SELECTABLE preset (create-token-flow) + zero-to-N tool-specific EXTRAS. ~80% of the state vocab is shared.

What this shows

  • signup_agent is universal — all 3 tools dispatch it. Already parameterized via OAUTH_PROVIDER env var (Google/GitHub branches in the prompt; Apple/email plausibly easy to add).
  • onboarding_doer is universally available but only dispatched when the tool's onboarding state is actually reached. (Vercel and Cursor accounts were pre-onboarded so the state never fired.)

  • One tool-specific dispatcher: Cursor's inline _dispatch_navigate_to_api_keys using path-2 click --text "API Keys". This is an ESCAPE HATCH the unified agent needs to support — arbitrary per-tool inline dispatchers for special transitions.

What this shows

  • Cost dropped sharply with each tool: Hyperbrowser 4 runs (template establishment), Vercel 7 runs (most failures were tool-specific edge cases: token format, modal timing, WAF), Cursor 3 runs (URL nav + token prefix only).
  • The chassis itself was correct from run 1 in all cases. All failures were in TOOL-SPECIFIC knobs (regex, prompt text, dispatch table cells) — never in the chassis loop, classifier, or sub-agent logic.
  • This is the empirical evidence the iteration-loop can be packaged. The failures were diagnosable from logs + screenshots, localized to the 5 swap points, and fixed via single-line edits. That's the signature of a packageable loop.

The unified agent spec precise enough to hand to the next implementation

Putting it all together: the input surface (ToolConfig), the agent's internals (which stay unchanged from the 3 wrappers), the success contract, and the iteration protocol. This is the spec that goes into the next phase's claude -p invocation or skill.

Input surface — ToolConfig dataclass

@dataclass
class ToolConfig:
    # 1. URL (the only mandatory swap)
    name: str                          # used for session name + recording dir
    url: str                           # target start URL

    # 2. Vendor token shape (mandatory)
    key_regex: str                     # e.g. r"^vcp_[a-zA-Z0-9]{24,}$"

    # 3. OAuth provider (default: google)
    oauth_provider: Literal["google", "github", "apple", "email"] = "google"

    # 4-5. Tool-specific state vocab extras + dispatch overrides (optional)
    extra_states: dict[str, str] = field(default_factory=dict)
    dispatch_overrides: dict[str, Callable] = field(default_factory=dict)

    # Token-extraction pattern (default: create-then-reveal w/ vision)
    extraction_pattern: Literal["dashboard_visible", "create_with_modal"] \
        = "create_with_modal"

    # Optional: screen recording on by default
    record: bool = True
    record_fps: float = 1.0

    # Optional: chassis paths needed (the LLM picks; this is a hint)
    chassis_paths: set[int] = field(default_factory=lambda: {1, 2})  # 3 on demand

The unified agent's main loop — IDENTICAL across the 3 instances

def run_unified_login_to_get_api(config: ToolConfig) -> dict:
    """Returns final JSON: {status, tool, api_key, summary}"""

    # Merge config's extras with the 5 universal states + create-token preset
    state_vocab = build_state_vocab(config)
    dispatch_table = build_dispatch_table(config)

    # Identity loaded from doppler accounts/oauth (per OAUTH_PROVIDER)
    os.environ.setdefault("OAUTH_PROVIDER", config.oauth_provider)

    # Optional recorder
    recorder = start_recorder(config) if config.record else None

    try:
        ensure_tab_for_cold_start(config.name, config.url)
        for outer in range(1, MAX_OUTER_ITER + 1):
            cls = classify(config.name, states=state_vocab)
            if check_terminal_state(cls): return terminal_response()
            dispatch = dispatch_table.get(cls["state"])
            outcome, trace = dispatch(config.name, config.url)
            if outcome == "done":
                key = extract_or_vision(trace, config)
                if config.key_regex_match(key):
                    return done(key, summary=...)
        return failed("max_outer_iter exceeded")
    finally:
        if recorder: recorder.terminate()

What "shared surface area" looks like in one paragraph

For the precise comment you mentioned wanting to write:

The shared surface area: 6 shared library files (agent_core.py, state_classifier.py, signup_agent.py, onboarding_doer_agent.py, get_api_agent.py, create_token_agent.py, plus optional screen_recorder.py) totaling ~1500 LoC, used identically by every tool wrapper. The wrapper itself is ~270 lines but only 5 specific values vary per tool: (1) URL, (2) key_regex, (3) oauth_provider, (4) extra_states dict (over the 5 universal states + 1 selectable create-token preset), (5) dispatch_overrides dict (state → callable). Identity credentials are externalized to doppler accounts/oauth (per-provider env vars: GOOGLE_OAUTH_EMAIL, GITHUB_OAUTH_EMAIL, etc.). Token extraction uses vision (claude -p with @<path> attachment) as the primary mechanism for create-with-modal tools, DOM-regex as the primary for dashboard-visible-key tools. The chassis exposes 13 action verbs across 3 identification paths (AX-tree index, DOM selector via opencli native --text/--testid/--role, pixel-coordinate via eval) — sufficient for all chassis-friendly and most chassis-unfriendly sites without further extension. Empirically validated across N=3 tools spanning Google + GitHub OAuth, dashboard-visible-key + create-with-modal extraction patterns, and same-domain + separate-subdomain auth substrates.
