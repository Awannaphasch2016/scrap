The handler change · what would actually ship

Roughly 25 lines added to curator/core/handler.py, gated on the new event.action string so the daily SNS-fan-out invocation still routes to the normal curator pipeline unchanged. 

def lambda_handler(event, context):
    _prepare_writable_layout()
    _fetch_doppler_secrets()
    _configure_egress()
    _log_egress_ip()

    # NEW · one-shot ops branch · doesn't touch the curator topics
    action = (event or {}).get("action")
    if action == "configure-schema-exposure":
        return _configure_schema_exposure(event.get("schemas", ""))

    # ...existing CURATOR_TOPIC dispatch unchanged...
    topic_module = _resolve_topic_module()
    import_module(topic_module).main()
    return {"status": "ok"}


def _configure_schema_exposure(schemas: str) -> dict:
    """Run the one SQL pair that exposes a set of schemas to PostgREST.
    `schemas` is a comma-separated string; passed verbatim into the SQL value.
    """
    import psycopg2
    dsn = os.environ["SUPABASE_DATABASE_URL"]
    with psycopg2.connect(dsn, connect_timeout=15) as conn:
        conn.autocommit = True
        with conn.cursor() as cur:
            cur.execute("ALTER ROLE authenticator SET pgrst.db_schemas TO %s", (schemas,))
            cur.execute("NOTIFY pgrst, 'reload config'")
            cur.execute("SELECT rolconfig FROM pg_roles WHERE rolname='authenticator'")
            rolconfig = cur.fetchone()[0]
    logger.info("schema exposure configured · rolconfig=%s", rolconfig)
    return {"status": "ok", "schemas": schemas, "rolconfig": rolconfig}

The caveat · this might not stick

Supabase Cloud may overwrite role-level config on its next dashboard config save. The PostgREST db-schemas setting is conceptually a project-level config that Supabase's dashboard config service owns. When you save anything in Settings → API, the service re-writes its full PostgREST config — and may stomp on role-level overrides you set via SQL.

Path B works right now, but if you ever click Save on any API setting in the dashboard, you may need to re-run Path B. The durable fix is still Path A (add curator to Exposed schemas in the dashboard) because that's the source the config service reads from.

Practical sequence: Path B unblocks you in 60 seconds; Path A is the durable lock. Run B if you can't get to the dashboard right this moment; do A whenever you next have it open.

What Path B is NOT

  • It's not a workaround for any auth or RLS problem. The schema's GRANTs and RLS policies are already correct (verified in Stage A of the Supabase migration). The only missing piece is PostgREST's db-schemas allow-list — Path B writes to exactly that, nothing else.
  • It's not idempotent across dashboard saves. The dashboard's config service owns the canonical truth; SQL-side overrides can be silently overwritten. See the caveat above.
  • It's not a privilege escalation. The Lambda already has SUPABASE_DATABASE_URL (with embedded postgres-superuser password) for its daily write path. ALTER ROLE authenticator SET … is well within that capability. No new IAM, no new Doppler secret.
  • It's not the right answer if you can click the dashboard. Path A is faster (10s vs ~5 min including the handler code change), more durable, and uses the channel Supabase tells you to use.
