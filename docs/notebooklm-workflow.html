NotebookLM workflow — implementation reference

How curator ask (Node, on laptop) and news_curator.NotebookLMUploader (Python, in Lambda) both reach NotebookLM through the same notebooklm-py + Playwright substrate, with a single storage_state.json cookie blob as the shared auth artifact. Two distinct workflows (upload + query) share most of the architecture but differ in caller and trigger.

L1 · Context system as black box

The highest-level view — the curator+Lambda system on one side, NotebookLM + Google Accounts + Doppler on the other. Two operator paths: query-time (curator ask) and auth-rotation-time (notebooklm login → writes storage_state.json). The redirect-on-expiry edge to Google Accounts is what surfaces in failure logs as "Authentication expired or invalid".

L2 · Container Two callers, one shared substrate

Both the Lambda-side NotebookLMUploader (Python, lazy-imports notebooklm-py as a library) and the laptop-side curator CLI (Node.js, shells out to the notebooklm CLI binary) end up driving Playwright + Chromium to interact with NotebookLM. The shared dependency is a storage_state.json cookie blob — written once by the operator running notebooklm login, then either read directly from ~/.notebooklm/ (laptop) or stored in Doppler as NOTEBOOKLM_STORAGE_STATE and materialized to /tmp/.notebooklm/storage_state.json at Lambda cold-start.

L3 · Component inside the Lambda · upload path

Drilling into the Lambda container to show the actual components that participate in the upload path. NotebookLMUploader calls _ensure_notebooklm_storage() first (materialize Doppler-injected env to ~/.notebooklm/storage_state.json if absent), then lazy-imports notebooklm-py and uses NotebookLMClient.from_storage() as an async context manager. The .sources namespace on the client is what carries the three methods we actually use: list, delete, add_file.

Sequence · Lambda upload cron path · digest.md → notebook source

Daily 06:00 UTC cron path. EventBridge fires the Lambda; the handler runs Doppler fetch + residential-proxy chain (abbreviated here — see the residential-proxy showcase page) and then invokes news_curator.main(). The pipeline writes /tmp/digest.md and hands it to NotebookLMUploader.upload(). The uploader lazy-imports notebooklm-py, ensures the storage_state file is materialized from the env-injected secret, launches a Playwright Chromium instance, deletes any prior digest.md source on the notebook (rotation — one current digest, not one per day), then uploads the fresh file.

Sequence · curator ask laptop path · query a notebook

Operator-triggered query path. curator ask <topic> <query> resolves the topic to a notebook_id, then shells out to the notebooklm CLI binary (installed via pip install notebooklm-py[browser]) with --json. The CLI launches its own Playwright Chromium with the laptop's ~/.notebooklm/storage_state.json, navigates to the notebook, types the query, waits for the response stream, extracts the answer + citations, and emits JSON on stdout. curator's notebooklm.mjs parses the JSON and returns {answer, raw} to the calling command.

Operational notes

storage_state.json expiry is the most common failure: NotebookLM session cookies expire on a Google-side schedule (typically weeks, not days). When that happens, BOTH workflows fail at the same point — Playwright navigates to the notebook URL, gets redirected to accounts.google.com/ServiceLogin, and notebooklm-py raises "Authentication expired or invalid." The fix is the same in both cases: run notebooklm login on the laptop (interactive browser flow), then either (a) let curator pick up the new ~/.notebooklm/storage_state.json automatically, or (b) push the new blob to Doppler so Lambda picks it up at next cold-start: doppler secrets set NOTEBOOKLM_STORAGE_STATE="$(cat ~/.notebooklm/storage_state.json)" --project scrape --config dev.
Source rotation in upload: the uploader deliberately deletes any prior source whose title == "digest.md" before uploading the fresh one. This keeps the notebook holding exactly one current digest rather than one-per-day. Side-effect: NotebookLM has no historical record of past digests on its side — if you want history, archive digest.md to S3 or commit it from the Lambda. (Currently not done — could be a V2 add for the observability page.)
The two callers use the same package differently: Lambda uses notebooklm-py as a Python library (lazy-imports NotebookLMClient and calls async methods); curator shells out to the same package's CLI binary. Both end up doing the same Playwright work internally. The choice was pragmatic — the Lambda already imports Python deps so a library is natural; curator is Node and shelling out keeps the Node side small.
NotebookLM upload doesn't use the residential proxy: by design, HTTP_PROXY is set before news_curator imports, but the uploader path doesn't use requests — it goes straight through Playwright + Chromium, which doesn't honor the env var. That's fine because NotebookLM accepts AWS-IP traffic (Google doesn't gatekeep on source IP class the way Reddit does). Only Reddit fetches need the residential proxy.
