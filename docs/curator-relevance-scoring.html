Rank by relevance how the curator marries demand (job listings) with supply (your skill profile)

The jobs topic ships with a relevance scorer baked into the pipeline. This page walks through how it works — the two inputs, the scoring algorithm, where the result is stored, and what's intentionally NOT in the model.

One-sentence model: every job item is scored by counting weighted keyword hits between the item's (title, tags, content) and a hard-coded SKILL_WEIGHTS dict (your supply profile). Title hits count 2×, tag & content hits 1×. The score is stored on each row, used by the UI's sort by relevance toggle, and gates what makes it into the daily digest.

The two sides

SUPPLY · your skill profile

A Python dict at curator/topics/jobs.py:54-80 (SKILL_WEIGHTS): keyword → numeric weight, organised in three rough tiers. Tuned manually to match Anak's portfolio. Not learned, not in the DB, not sourced from preferences / scenario / patterns CLIs. Updating it = code edit + Lambda redeploy.

A small NEGATIVE_KEYWORDS list at line 82 carries deal-breakers ("on-site only", "us citizen only", etc.) with a flat -5.0 penalty per hit. Anti-supply, essentially.

DEMAND · the incoming job stream

Seven fetchers (HN Who-is-hiring, RemoteOK, Remotive, WeWorkRemotely, r/forhire, r/MachineLearningJobs, r/jobbit) emit Item objects with title, content, and (for RemoteOK) metadata.tags. The pipeline calls score_item(item) on each one before upsert.

Items below RELEVANCE_THRESHOLD = 1.0 (configurable via JOB_RELEVANCE_THRESHOLD env var) are still stored, but excluded from the digest + top-N markdown artifacts.

The supply dictionary, by tier

Tiers aren't a code construct — the file comments group keywords by intent. Higher weight = bigger contribution to score per hit.

TierIntentSample keywordsWeight range
A — direct match jobs that are this is what I do web scraping, mcp, ai agent, rag, meta ads, ai automation, n8n 3.0 – 4.0
B — broad skill jobs that use my tools aws, python, typescript, supabase, astro, cold email, telegram bot 1.0 – 2.5
C — adjacent I could plausibly take it osint, blockchain, trading, fintech 0.5 – 1.0
— negative deal-breaker, subtract on-site only, no remote, us citizen only −5.0 each

The scoring algorithm

Implemented at curator/topics/jobs.py:127-154. Here it is in essence: 

def score_item(item) -> tuple[float, list[str]]:
    score = 0.0
    matched = []
    for keyword, weight in SKILL_WEIGHTS.items():
        hits = 0
        if keyword in item.title:    hits += 2   # title weighted 2×
        if keyword in item.tags:     hits += 1
        if keyword in item.content:  hits += 1
        if hits:
            score += weight * hits
            matched.append(keyword)
    for negative in NEGATIVE_KEYWORDS:
        if negative in item.title or negative in item.content:
            score -= 5.0
    return score, matched

The real implementation uses precompiled regex with \b word boundaries and case-insensitive flags — but the math is the same: title hits count double, tags + content count single, weights multiply hits, and a hit anywhere adds the keyword to matched for later inspection.

Newsfeed top-15 Browser, client-side allItems.sort(byRelevance).slice(0, 15) — the cross-topic curated landing view.
Digest gate jobs.py:362-412 Items with score < threshold (1.0) excluded from jobs_digest.md and from today's digest / top-N artifacts. Stored in DB regardless.
Top-N digest jobs_topN_YYYY-MM-DD.md Today's items sorted by relevance, sliced to top 10. The "best matches" feed.

What's intentionally NOT in the model

No machine learning. No embeddings. No personalisation loop.

The whole supply profile is a hand-tuned dict. There's no semantic similarity, no LLM call, no labelled training data, no clicks-feedback. A job that talks about "computer vision for retail" but never says cv or vision in those exact words will score 0 even if it'd be a great fit for you. The model is fast, free, deterministic, and trivially debuggable — and that's the explicit trade.

No location / time-zone / pay parsing.

Remoteness is approximated only by the negative-keyword list (and even then only when sources are honest about it). Salary, time-zone, contract-vs-FTE are not scored — even though most fetchers expose them in the raw payload. Easy extension if you want it.

No supply-profile versioning or A/B.

Editing SKILL_WEIGHTS is a code change that takes effect on the next deploy. Past items keep whatever score they had when ingested (relevance is computed at insert/upsert, never recomputed) until the same item is re-scraped and upserted — at which point it gets re-scored with the new weights. So the corpus mixes old + new scoring conventions after a weight change.

How to tune

  1. Edit SKILL_WEIGHTS in curator/topics/jobs.py — add a keyword, bump a weight, demote one to a lower tier.
  2. Add deal-breakers to NEGATIVE_KEYWORDS if a particular phrase keeps surfacing irrelevant matches.
  3. Tweak RELEVANCE_THRESHOLD (env: JOB_RELEVANCE_THRESHOLD) if too much / too little is reaching the digest. Default 1.0 is intentionally lenient.
  4. Redeploy the jobs Lambda. New scores apply to items fetched after the deploy; old items keep their pre-change scores until re-scraped.
