A trace of what happened when curl_cffi tried to fetch the Upwork job search page, and what a real browser would have done differently.

3. Plain-English step list

  1. Our Python script sent a normal HTTPS GET request to Upwork's search URL, with curl_cffi impersonating Chrome 120's TLS fingerprint and User-Agent.
  2. The request never reached Upwork. It hit Cloudflare, which sits in front of Upwork as a reverse proxy and bot-protection layer.
  3. Cloudflare inspected the request and saw red flags: no cf_clearance cookie, no prior browsing session, an IP it didn't recognize as human-trusted. Even though the TLS fingerprint looked like Chrome, the absence of a prior browser session was enough.
  4. Cloudflare returned HTTP 403 with the header cf-mitigated: challenge, and a body containing an HTML page with embedded JavaScript — the "challenge."
  5. A real browser would run that JavaScript, compute a token, set cf_clearance, and retry. curl_cffi is just an HTTP client — it has no JS engine, so the challenge sits unread.
  6. Our script saw 344 KB of HTML titled "Challenge - Upwork" and zero job data. From Cloudflare's perspective, the request was never trusted enough to be forwarded to Upwork's origin servers.

4. What this means for the build

Any scraping approach that lacks a JavaScript runtime will fail at step 4. That includes requests, httpx, curl_cffi, and any pure-HTTP library — regardless of how convincingly they impersonate Chrome's TLS or headers.

The two real options are:

  • Headless browser (Playwright + Chromium) — has a real JS engine, solves the challenge automatically, but adds ~200 MB of browser binaries and 5–10 s per page load.
  • Reuse an existing authenticated session — paste a logged-in user's cf_clearance and session cookies into the script. Bypasses the challenge entirely. Risks the account if Upwork detects scraping.
