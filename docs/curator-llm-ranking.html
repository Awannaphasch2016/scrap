Rank via claude -p LLM scoring · supply (profile) meets demand (jobs) · sequence-diagram view

This is the v0 of swapping the regex-based score_item for an LLM judgment. The two scorers are alternatives, not a hybrid — once the LLM scorer is trusted, the regex one goes away.

One-sentence model: a driver script (running on the laptop on a schedule) reads each item from the DB, builds a prompt that combines your profile paragraph (supply) with the item's title + content (demand), shells out to claude -p for a JSON-shaped {score, reason} verdict, and writes the result back to curator.items.relevance (plus metadata.llm_reason for audit).

The two inputs

SUPPLY · your profile (prose, not a dict)

A hand-authored paragraph at curator/topics/jobs_profile.md (new file). Replaces SKILL_WEIGHTS. Roughly: who you are, what you build, what stack, what you charge, what you refuse (e.g. on-site, US-only). The LLM reads this once per invocation as the standard of comparison.

"Tune the scorer" no longer means bumping numbers in code — it means editing this paragraph. Different ergonomics, but it can capture nuances the dict can't (e.g. "prefer agency work over direct-to-founder, prefer 2-6 week scopes over 6-month full-time").

DEMAND · job items already in the DB

Unchanged from today. The Lambda pipeline still fetches Reddit/HN/RemoteOK/etc. and upserts items into curator.items. What changes is what fills the relevance column afterwards.

Where it runs (v0)

On the laptop, manual or cron — not in the scraper Lambda. Three reasons:

  • claude CLI is already authenticated locally (your Anthropic subscription); auth-in-Lambda would need either an API key (different billing) or pre-warmed credential plumbing.
  • ~30 items/day takes ~5 minutes wall-clock; on-laptop is fast enough and easy to inspect.
  • Decouples the experiment from the production scraper — if the LLM scorer behaves badly, the Lambda + UI are unaffected.

The prompt (template)

# sent on stdin to: claude -p
You are evaluating job listings for fit against a freelancer's profile.

PROFILE
=======
{profile_paragraph}

JOB LISTING
===========
Title:  {item.title}
Source: {item.source_name}
Author: {item.author}

{item.content}

INSTRUCTIONS
============
Score this listing from 0 to 10 for fit, where:
- 0-2  = clearly not a fit (wrong stack, on-site only, US-only, etc.)
- 3-5  = adjacent · could plausibly take it but not the obvious choice
- 6-8  = solid fit · profile matches multiple aspects
- 9-10 = exceptional match · ideal client / role / scope

Return ONLY a JSON object, no markdown fences, no prose:
{"score": <float 0-10>, "reason": "<one sentence justifying the score>"}

What's NOT in v0

No hybrid / combination.

The regex scorer is not running alongside as a fallback or pre-filter. When we enable the LLM scorer, it owns the relevance column entirely. Easier to reason about, easier to evaluate ("is the LLM ranking good enough on its own?").

No re-scoring of old items on profile change.

Each item is scored once (when the driver first sees it). If you edit the profile paragraph, only items scored after the edit reflect the new judgment. Existing items keep their stale scores until they age out of the window or you add a "rescore everything" command.

No concurrency.

One claude -p at a time. Plenty fast for ~30 items/day. Async/batch would matter only at much larger volume.

No removal of the regex code yet.

score_item and SKILL_WEIGHTS stay in jobs.py during the trial. The Lambda still computes a regex score (cheap) and writes it to relevance; the laptop driver overwrites that value with the LLM score after the item lands. Once the LLM scorer is trusted, we delete the regex path in a follow-up commit (one-line change in the pipeline + delete dead code).
