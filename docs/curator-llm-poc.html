claude -p relevance scorer · PoC throwaway demo · ~60 lines · no DB, no infra change, no integration

Goal: prove the LLM scoring idea works in isolation before designing the integration. A single Python file with hand-coded inputs, shells out to claude -p, prints the result. Run it three times, eyeball whether the scores are sensible and how much they vary. That answer decides whether we build the integration at all.

One-sentence model: experiments/llm_scorer_poc.py embeds a profile paragraph + 2-3 real job listings, builds one prompt per item, spawns claude -p, parses {score, reason} JSON, prints to stdout. Nothing else.

The file

# experiments/llm_scorer_poc.py · throwaway
import subprocess, json, sys

PROFILE = """
Anak is a freelance AI / automation engineer based in Bangkok.
Builds: LLM agents, web scrapers, MCP servers, marketing automation,
Telegram / Discord bots, Astro / Next.js frontends, AWS Lambda backends.
Stack: Python, TypeScript, AWS, Supabase, Pulumi. Comfortable with
Anthropic Claude API + Claude Code CLI as primary LLM tooling.
Prefers remote, contract or project-scoped work (~2-6 weeks). Refuses
on-site, US-only, full-time-employment-only postings.
""".strip()

ITEMS = [
    {
        "title":  "Senior Python Engineer · LLM Infrastructure · Remote",
        "author": "Vercel",
        "content": "We're building the AI SDK infra. Python 3.12, FastAPI, "
                   "Postgres + pgvector, AWS Lambda + Bedrock. Remote OK.",
    },
    {
        "title":  "[Hiring] WordPress site cleanup, ~$300",
        "author": "lazyowner",
        "content": "Old WP site, plugin mess, need someone to audit + clean.",
    },
]

RUBRIC = """
Score 0 to 10 for fit:
  0-2  not a fit (wrong stack, deal-breakers like on-site)
  3-5  adjacent · could plausibly take but not obvious
  6-8  solid fit · profile matches multiple aspects
  9-10 exceptional · ideal client / role / scope
Return ONLY: {"score": <float>, "reason": "<one sentence>"}
""".strip()

def score(item):
    prompt = f"PROFILE\n=======\n{PROFILE}\n\nJOB\n===\n" \
             f"Title: {item['title']}\nAuthor: {item['author']}\n\n" \
             f"{item['content']}\n\n{RUBRIC}"
    r = subprocess.run(
        ["claude", "-p", prompt],
        capture_output=True, text=True, timeout=60,
    )
    if r.returncode != 0:
        return {"error": f"claude exit {r.returncode}: {r.stderr[:200]}"}
    try:
        return json.loads(r.stdout.strip())
    except json.JSONDecodeError as e:
        return {"error": f"bad JSON: {e}", "raw": r.stdout[:200]}

for item in ITEMS:
    print(f"\n=== {item['title'][:60]} ===")
    print(json.dumps(score(item), indent=2))

Sequence — one PoC run

Operator runs the script; for each hard-coded item the script renders a prompt, spawns claude -p, captures stdout, parses JSON, prints. No I/O outside stdout. The "Claude API" is implicit — the CLI handles HTTPS internally; from our side it's a subprocess that returns text.

What we learn from running it

  • Does claude -p return parseable JSON? Or does it wrap the output in ```json … ``` fences, add prose commentary, or both? If yes → either tighten the prompt ("return ONLY the JSON object, no markdown fences, no other text") or strip fences in the parser.
  • Are the scores roughly ordered correctly? The Vercel listing should score high (Python + LLM infra + remote, all bullseye); the WordPress cleanup should score low (off-stack, micro-scope, no AI angle). If the ranking is upside-down, the prompt or the profile needs work, not the integration.
  • How much do scores vary across runs? Run it three times on the same items. If the same job gets 8.2 / 7.9 / 8.1 → fine, ship it. If 8 / 3 / 9 → we need temperature control, JSON Schema output, or multi-sample averaging before this is usable.
  • How long does one call take? CLI startup + Claude response. If < 10 s, on-laptop nightly is comfortable. If > 30 s × 30 items = 15 min → still fine for daily, painful for ad-hoc.

Decision gate · what gets built next

If the PoC looks good (JSON parses, ordering sensible, variance acceptable) → revisit the full integration design — write rescore.py, wire it to PostgREST, decide on schedule. The blast-radius diagram on that page becomes load-bearing.
If the PoC looks bad (malformed output, wrong ordering, wild variance) → don't integrate yet. Iterate on the prompt, or add structured-output enforcement (JSON Schema, temperature pinning), or admit the model isn't a fit for this task and stick with the regex scorer.
