L1 — Context login-agent as a black box · who/what it talks to

The outsider's view. Anak issues tasks through Paperclip's REST API; the system drives Chrome through the auth flow at target websites, leaning on Google OAuth, Anthropic (claude -p) and OpenRouter (Gemini for browser-use), with credentials from Doppler and identity from pw profile.

What L1 settles

  • Two LLM channels: claude -p for chassis-native agents, Gemini Flash Lite via OpenRouter for browser-use scripts. Same external contract from outside.
  • Doppler is the only secret store; per-site credential conventions match each upstream wrapper's expectations.
  • Paperclip is treated as an external system here because L1 is about the boundary of the login-agent, not the orchestrator above it.

L2 — Container deployable / runnable units inside the system

What runs as what. The bash composer is the unit Paperclip dispatches to; it then spawns 8 sub-agent processes across two LLM stacks (opencli + claude-p for the chassis-native four, browser-use + Gemini for the three subprocess-wrapped externals). Both stacks drive the same Chrome.

What L2 settles

  • Chassis-native sub-agents share agent_core.py as a Python library, then talk to opencli (which talks to Chrome).
  • Subprocess-shim sub-agents (form_fill_signup_agent.py, two_fa_bypass_agent.py, login_type_detector.py partially) own NO ReAct loop themselves — they shell out to existing browser-use scripts that drive Chrome via their own session.
  • The composer is bash, not Python. It only does subprocess + JSON parse + branch — no LLM, no opencli of its own.
  • Paperclip's MCP server is included as a future control surface; v1 uses REST.

L3 — Component inside agent_core.py · the chassis internals

Zoom into the shared library that every chassis-native body imports. ~253 lines. Sensor (opencli helpers), policy (ask_llm + BASE_PROMPT), actuator (execute dispatcher), main loop (run_agent), one entry point per body file.

What L3 settles

  • Body files only ever interact with three entry points: build_arg_parser(), AgentConfig(...), and run_agent(...). Everything else is internal.
  • The only two external CLIs the chassis spawns are opencli (every sensor/actuator call) and claude (one call per loop iteration via ask_llm). Both go through _run.
  • v1 plan adds NOTHING to agent_core.py — the chassis is KEPT in its current shape. The "new in this plan" pieces are bodies and shims, not chassis modifications.

L4 — Class the fractal-substitution payoff visualized

The same external CLI contract (run as python scripts/<name>.py [args], emit final-line JSON to stdout) is satisfied by two completely different internal shapes: chassis-native bodies (instantiate AgentConfig + call run_agent) and subprocess-shim bodies (shell out to a wrapped external script and parse its output). The composer dispatches both kinds identically.

What L4 settles — the principle in code form

  • External contract sacred, internal implementation free. Composer treats every sub-agent the same: subprocess.run → check exit code → read last-line JSON → branch. It cannot tell which agents use the chassis and which are shims.
  • Two stacks coexist by design. Chassis-native = opencli + claude-p (~$0.20/run, high control). Wrapped externals = browser-use + Gemini Flash Lite (~$0.01/run, less ceremony). Both ship in the same plan because each capability picks the lighter implementation it already has.
  • v2 fan-out is a refactor, not a rewrite. Each subprocess call in the composer becomes a sibling Paperclip role with its own parent/sub-issue. The body code (chassis-native OR shim) never changes — only the dispatch layer above it.
